# خطة تطوير قسم الأتمتة — بن العجوز ERP

## الهدف

تحويل قسم الأتمتة من لوحة عرض وتشغيل يدوي إلى محرك تشغيل ومراقبة تلقائي موثوق، يعمل أساسًا على السيرفر الأونلاين، ويستخدم السيرفر المحلي كمسار استرداد عند انقطاع الاتصال.

## النطاق

- جدولة حقيقية للمهام حسب توقيت القاهرة.
- تنفيذ المهام خارج طلبات HTTP من خلال Worker وQueue.
- تشغيل الأتمتة المرتبطة بالأحداث: البيع، الإلغاء، الخصم، المخزون، الوردية والمزامنة.
- سجل تنفيذ كامل وقابل للبحث.
- منع التكرار وإعادة المحاولة الآمنة.
- لوحة رئيسية متحركة ذات طابع Operations Command Center.
- حماية الأسرار ونقلها إلى متغيرات البيئة.

## التصميم المعتمد

### 1. التشغيل

يتكون النظام من Scheduler يقرأ المهام المفعلة، وWorker ينفذها، وQueue تدير المحاولات وإعادة التشغيل. كل تنفيذ يحصل على `execution_id` فريد لمنع التكرار. السيرفر الأونلاين هو المصدر الأساسي، والسيرفر المحلي يسجل المهام المؤجلة ويرسلها عند عودة الاتصال.

### 2. المهام

يتم توحيد مفاتيح المهام، وإلغاء المسارات العامة التي تعيد نجاحًا وهميًا. كل مهمة يجب أن تمتلك معالج تنفيذ صريحًا، وإعدادات، وقنوات إخطار، وحدودًا واضحة للفشل وإعادة المحاولة.

### 3. الأحداث

ينشئ النظام Event Bus داخليًا ببيانات موحدة: `event_id`, `event_type`, `branch_id`, `user_id`, `entity_id`, `created_at`, و`payload`. يتم ربط الأحداث بإجراءات الأتمتة مع Idempotency.

### 4. البيانات والسجل

يتم تفعيل جدول `automation_logs` لحفظ البداية والنهاية والمدة والحالة والخطأ والنتيجة. يتم إصلاح استعلامات المخزون لتستخدم `inventory.quantity` و`products.min_stock` بدل الأعمدة غير الموجودة.

### 5. اللوحة الرئيسية

الصفحة الرئيسية تعرض حالة المحرك، المهام النشطة، النجاح والفشل، المهام المتأخرة، متوسط زمن التنفيذ، وآخر تنبيه. تعرض Timeline ومصفوفة صحة المهام ورسم تدفق الأحداث. الحركة مقتصرة على التحديثات الحقيقية مع دعم `prefers-reduced-motion`.

## مراحل التنفيذ

1. إزالة الأسرار من الملفات وتدوير المفاتيح.
2. توحيد سجل المهام والمفاتيح والمعالجات.
3. بناء Scheduler وWorker وQueue.
4. ربط أحداث النظام بالأتمتة.
5. بناء سجل التنفيذ وواجهات الفلترة والتفاصيل.
6. إعادة بناء Dashboard والرسوم الحديثة.
7. إضافة Recovery للمحلي والمزامنة الآمنة.
8. اختبار الفشل والانقطاع والتكرار والصلاحيات.
9. نشر تدريجي مع مراقبة النتائج.

## معايير القبول

- لا تعمل مهمة معطلة.
- لا يتم تسجيل نجاح دون تنفيذ فعلي.
- لا يتكرر التنبيه أو الأثر المالي عند إعادة المحاولة.
- كل مهمة مجدولة تظهر بآخر تشغيل ونتيجته.
- ظهور الخطأ مع سبب قابل للمعالجة.
- استمرار تسجيل المهام عند انقطاع الأونلاين وإرسالها بعد عودة الاتصال.
- اجتياز اختبارات الوحدة والتكامل واختبارات السيناريوهات المالية.

## سجل القرارات

- اعتماد تصميم هجين: الأونلاين أساسي والمحلي للاسترداد.
- استخدام Worker وQueue بدل تنفيذ المهام داخل HTTP.
- جعل Dashboard التشغيلي هو الواجهة الرئيسية، والرسم الشبكي عرضًا تقنيًا اختياريًا.
- اعتبار كل عنصر في الواجهة مرتبطًا بمؤشر أو قرار تشغيلي واضح.
